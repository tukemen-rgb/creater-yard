# 自動で作り続けるときの決まり（CreatorYard 版）

無人で回す前提の作業規則。原本（動いている版）は GAMEYARD の
`tukemen-rgb/site` の `docs/autonomous-loop.md`。ここには CreatorYard の
実情に合わせた版を置く。**判断に迷ったら止まって聞く**のではなく、
**判断に迷うことをそもそも作業に含めない**（迷う類のものは人＝社長が決める）。

## 分担（**2 時間で 1 サイクル**・1 役割の持ち時間は 20 分）

**2026-08-09 20:35 に社長の指示で「1 時間 5 回」から「2 時間 5 回」へ変更。**
時刻は **JST**（予約は UTC なので、cron の時は JST と 9 時間ずれる）。

| 時刻（JST） | 担当 | 役割 |
| --- | --- | --- |
| **毎時 :00** | **gdp（ChatGPT）** | 戦略・設計レビュー。**2 時間で 1 つのお題**を進め、**1 時間に 1 回**は連携が来る |
| 偶数時 :10 | Claude ① | 調査・提案 |
| 偶数時 :30 | Claude ② | 技術設計 |
| 偶数時 :50 | Claude ③ | 実装 |
| 奇数時 :10 | Claude ④ | 監査・報告 |
| 奇数時 :30 | Claude ⑤ | 調停 |

- **gdp の :00 は毎時のまま。**Claude 側が 2 時間かけて 1 周する間に、
  gdp からの連携は **2 回**来る。①と⑤は**前回の自分の周からの増分を
  まとめて見る**（1 回ぶんだけ見て取りこぼさない）
- **④が見る範囲は「前回の④レポート以降」＝およそ 2 時間**
- **持ち時間が 10 分から 20 分になった。**20 分に収まらない処理は
  background で回し、次の役割は見送る（規則 3）。③が拾い直すのは
  **2 時間後**なので、途中で切らずに完走させるほうが結局早い
- 予約の cron（UTC）: ① `10 1-23/2` / ② `30 1-23/2` / ③ `50 1-23/2` /
  ④ `10 0-23/2` / ⑤ `30 0-23/2`。**UTC の奇数時＝JST の偶数時**

往復は **AI Review Board =
[Issue #1](https://github.com/tukemen-rgb/creater-yard/issues/1)** で行う。
gdp は呼ばれたときだけ動く（社長が起動する）。動いたほうが Issue に書く。

- 前の周がまだ走っていたら重ねずに見送る

## 共通ルール（毎回・全役割）

1. **観測する場所は 4 つ。Issue #1 だけではない。** それぞれ総数だけを確認し、
   **前回確認時から増えたときだけ**最後のページを読む。増えていなければ読まない。

   | 場所 | 何があるか |
   | --- | --- |
   | **Issue #1** | AI Review Board。Claude の報告と、gdp・社長の連絡 |
   | **Issue #2** | **経営企画・社長代理 定時レビュー。gdp 側の本体**（5 軸評価つきの経営判断が 2 時間ごとに積まれる） |
   | **開いている PR のうち最新** | 統合の窓口。受入条件・実装依頼・許可がここに出る |
   | **`origin/main` の頭** | **正本。**`git fetch origin main` して頭が動いていないか見る |

   **`origin/main` を足した理由（2026-08-14）:** 社長は
   **PR #4 のコメントだけで 4 件を決めて、そのままマージした**
   （マージ承認・問い合わせ窓口・運用体制・ドメイン確定）。
   Issue #1 にも Issue #2 にも来ていない。**社長はその時いちばん動いている
   場所に書く。**そして④は `git fetch` と `git diff` しか見ていなかったので、
   **マージの 9 分前に「マージは未実施」と報告した。**
   **PR は閉じるが、main は必ず在る。**

   **なぜ 1 つでは足りないのか（2026-08-10 の失敗の記録）:** この規則がもともと
   「Issue #1 のコメント総数だけ」だったため、**⑤は 18 周にわたって
   「gdp 発言なし」と誤って報告し続けた。**実際には gdp は PR #4 に
   10 件以上、Issue #2 に 36 件を書いていた。**見る場所を間違えると、
   静かなのは相手ではなくこちらだと気づけない。**
   総数の記憶が失われたときだけ、最後のページを読み直す
2. **前の役割の処理（background 含む）がまだ走っていたら、この回は見送る。**
   走っている処理を**切り上げない**
3. **20 分に収まらない処理は background で回す**（重いビルド等）。
   終わるまで次の役割は見送りにする（持ち時間は 2026-08-09 に 10 分→20 分）
4. **変化が無い周は確認だけでスキップする。** commit も Issue への投稿もしない。
   短い間隔はトークン消費が大きい（90 分 1 本と比べ約 10 倍超）。
   この規則が効いて初めて成り立つ。**2 時間 1 サイクルにしても変わらない**
   - **「変化が無い」は「git に差分が無い」の意味。**「コードが動いていない」
     ではない。2026-08-09 に④がそう読み違え、①が事例 5 件・提案 2 件を
     足していた **5 時間 35 分**のあいだレポートを書かなかった
     （出典の質・推測の混入は①の主な事故要因なので、そこを誰も見ない
     時間ができていた。さかのぼって検査し問題は無かった）
   - ただし**コードに差分が無い周の④は短く書く**。何が増えたかの表と
     指摘だけでよく、検査項目の全表は要らない（消費を増やさないため）
   - **溜まっているときも作らない（背圧・2026-08-17 の⑤裁定）。**
     **開いている PR が 6 本を超えている間、③は新しい PR を作らない。**
     代わりに、既に開いている PR を**押しやすくする**仕事へ回る ——
     (1) **重なりの解消**（A を B に取り込む。押す回数そのものが減る）
     (2) **PR 本文の先頭に 3 行のまとめ**（各本文は 2,000〜4,000 字ある）
     (3) **統合通し検証** (4) それも無ければ**スキップ**。
     **止めたら理由と本数を必ず書く。黙って止まるのがいちばん悪い。**

     **例外 4 つ（これが無いと規則が害になる）**: ①社長の直接指示 ②本番が
     壊れている直し（白画面・データ消失・権利侵害） ③④⑤は止めない
     （監査と調停は PR を増やさない） ④①②も止めない（文書は PR にしない）

     **閾値 6 の根拠は n=1**。9 本まで溜まったときは丸 1 日 1 本も押されず、
     6 本のときは一度の作業で全部片付いた（2026-08-16）。**次に溜まった
     ときの実測で見直すこと。**根拠が 1 例であることを隠さない。

     **そして、これは 2 番目の手である。**まず **`W` を下げられないか**を
     問う ——「押す手間を減らせるか」「代行を申し出られるか」「1 本に
     まとめられるか」。2026-08-16 の詰まりは**作りすぎではなく、押し方の
     手順で止まっていた**（「マージして」の一言で 6 本が数分で入った）。
     **引き算から入ると、手が空いているのに何も進まない時間ができる。**
5. コードを触ったら `npm run lint`（ESLint＋型検査）と `npm run build`
   （静的書き出し）を通す。画面を触ったらブラウザで実物を見る
6. push 先は作業ブランチ。既定ブランチへ直接 push しない
7. Issue #1 への投稿には帰属フッターを付ける
8. commit は小さく分ける。大きな変更は理由をコードのそばに残す
9. **文書への追記で見出しを壊さない。** 記録ファイル（proposals / designs /
   case-studies / mediation / cycle-report）は「新しいものを上に」置くため、
   既存の見出しをアンカーにして差し込むことになる。**アンカーにした見出しは
   置換後の文字列の末尾に必ず再掲する**（忘れると、その見出しの `## <日時>` が
   消えて本文が前の項目に吸い込まれる。2026-08-09 に 29 か所を破損させ、
   git 履歴から復元した）。追記後は `grep -c '^## ' <file>` で見出し数が
   項目数と合うことを確かめる

10. **見出しに書く時刻は、実時計を見てから書く。** 前の周の表記に 1 時間を
    足して埋めない。書く前に必ず `TZ=Asia/Tokyo date` を実行する
    （コンテナの時計は UTC なので、そのまま `date` を読むと 9 時間ずれる）。
    **ループは止まることがある**（トリガの不発・セッションの切れ目）。
    止まった時間を「前の周の続き」として詰めると、記録全体が実時刻から
    ずれ、埋め合わせに「静穏運転で通過した周」のような**起きていない出来事**を
    書いてしまう（2026-08-09 に実際に発生。3 時間 50 分の停止を詰めた結果
    −2 時間のずれが固定され、実在しない「4 時台」を記録した）。
    ずれに気づいたら**過去の見出しは書き換えず**、その回のレポートに
    対応表を残して以後を実時刻に戻す（見出しの一括編集は規則 9 の事故を招く）

11. **「保存できるものは読み出せるか」を④の監査項目に入れる。**
    書ける・保存できる機能を作ったら、**同じ人がそれを読み出し・直せるか**を
    必ず確かめてから「完了」と記録する。2026-08-09 に、SPEC 実装順②
    （Story 投稿・**下書き**）を「完了」と記録していたのに、
    **下書き一覧も編集モードも作っていなかった**ことが 18 時間後に発覚した
    （API の `PUT /api/stories/<id>`・`GET /api/mine/stories` は両方あるのに
    画面が無い）。保存側だけを見て完了にしたのが原因。
    **画面に「あとで直せます」の類を書いたら、その手段が UI にあるかを
    その場で確かめる**

12. **API に新しい経路や手段を足したら、別オリジンから実際に叩いて確かめる。**
    このサイトは**本体（静的配信）と API が別オリジン**なので、
    ブラウザは CORS を通してしか API に届かない。**単体試験は node からの
    fetch で同一オリジン扱いになり、CORS を一切経ない**ので、
    ここの欠落は試験を何件足しても出ない。
    2026-08-09 に、`PUT /api/stories/<id>` の経路も認可も揃っていたのに
    `Access-Control-Allow-Methods` が `GET,POST,OPTIONS` のままで、
    **本番では編集が一切できない**状態を作っていた（ブラウザで保存を
    押して初めて発覚）。**新しいメソッド・新しいヘッダを使い始めたら、
    `OPTIONS` の応答にそれが載っているかを試験に足す**

13. **④は「素の `npm run build`」を必ず 1 回通す。**種を撒いた状態でしか
    ビルドしないと、**データが 1 件も無い場合**を誰も通さないまま進む。
    2026-08-09 に、公開 Story が 0 件だと `output: 'export'` が
    「missing generateStaticParams()」でビルドごと落ちる状態を作り、
    **clone した直後の機械では誰も `npm run build` を通せなかった**
    （実装も監査も毎回 `CY_DATA_DIR` に種を撒いていたので出なかった）。
    **種を撒いたビルドと、撒かないビルドの両方を通す**

14. **「本番の構成で、その対策は本当に効くか」を見る。**単体試験は
    node から直接叩くので、**逆プロキシも CDN も経ない**。
    2026-08-09 に、総当たり対策の鍵が `req.socket.remoteAddress` で、
    本番（`proxy_pass http://127.0.0.1:3010`）では**全利用者が
    同じ鍵**になり、誰かが 5 回失敗させるだけで全員が締め出される
    状態を作っていた。**試験は緑のまま**だった。
    規則 11（保存できるものは読み出せるか）・規則 12（別オリジンから
    叩く）と同じ形の見落とし。**対策を足したら、それが本番の経路で
    効くところまで確かめる**

15. **自分が赤くした試験は、その周のうちに緑に戻す。これは規則 3 に優先する。**
    規則 3（20 分に収まらなければ background）は**消費と衝突**を抑える
    ための決まり、規則 5（lint と build を通す・落ちたら直す）は
    **成果物の正しさ**の決まり。**ぶつかったら正しさを取る。**
    赤いまま周を終えると、次の役割が**壊れた土台の上で作業し**、
    しかも「前の周から落ちていた」ことに気づかない。
    - **超過してよいのは「自分が壊したものを直す」場合だけ。**
      新しい機能を作り続けるための超過は認めない
    - **直せないときは revert して緑に戻してから終える。**
      「commit しない」だけでは、作業中の赤い状態が残る
    - **超過したらレポートに必ず書き、次の役割を 1 つ見送る**
      （規則 3 の精神はここで残す）
    - 2026-08-10 に③が A-4 で 25 分超過した。`feed.mjs` の既定値を
      外したら既存の RSS 試験 2 件が落ち、直しきってから終えた。
      **この判断は正しい**（⑤ 03:37 の裁定）


16. **リポジトリの中に worktree を作らない。**`git worktree add` の追加先は
    **絶対パスで、リポジトリの外**（`/tmp/claude-0/...`）に置く。相対パスを
    渡すとリポジトリ直下に作業木ができ、作業対象と混ざる
    （2026-08-10 に④が実際に踏んだ。害は出なかったが取り除く手間がかかった）。
    使い終わったら `git worktree remove --force` で消し、`git worktree list` で
    残っていないことを確かめる

17. **コードを main へ入れる手順**（2026-08-14 に全面的に書き換えた。
    **PR #4 が merged / closed になり、それ専用だった条件の宛先が消えたため**）。

    もとの条件は「PR #4 が開いている間、そこへ集約する」ためのもので、
    **その中に「新規 PR は禁止」があった。前提が消えたので、この 1 つだけ外す。**
    **残りはそのまま生きている。**

    - **`main` に直接 push しない**（変わらない）
    - **`main` から新しい枝を切り、ドラフト PR を出す。**1 つの PR に 1 つの論点
    - **マージするのは社長だけ。AI はマージしない**（変わらない。**動かさない線**）
    - **force-push・履歴書き換え・無検証 merge は禁止**（変わらない）
    - **`docs/autonomous-loop.md` と `docs/research/` を PR に持ち込まない**

    - **着手前に remote head を再取得**（変わらない）
    - **push 後の remote head SHA で試験して報告**（変わらない）
    - **head を動かした周の担当が、同じ周に PR 本文の「最終SHA・試験件数」も直す**
      （2026-08-14 に⑤が追加。放っておくと gdp が別の枠をまるごと後追いに使う ——

      押し、さらに 8 分後に④が押して、また食い違った。**2 行の編集で済む**）
    - **本番 deploy・外部招待・秘密情報・本番データ・スポンサー関連の変更は
      行わない**（変わらない）

18. **指摘した本人が直してよいのは 2 つだけ。**
    (a) **秘密・認証情報が外へ出る経路**、(b) **註釈がコードより強いことを
    言っている**。この 2 つは④が見つけたその場で直してよい（見つけた人が
    直さないと、次の周まで漏れた状態・欺く註釈が残るため）。
    **それ以外は指摘に留め、③へ回す。**
    **「次の周まで置くほうが悪い」を理由に使わない** — 毎回それが言えてしまい、
    役割分担が消える（2026-08-14 に⑤が裁定。④の 08-13 の 2 件は (a)(b) に

19. **④の監査項目: 前の裁定で塞いだ穴が、いまの正本でも塞がっているか。**
    **正本が入れ替わっても、前に直したものは自動では付いてこない。**
    2026-08-09 23:35 に⑤が裁定して塞いだ穴（逆プロキシの下で

    **何をもって直ったとするかを④が決めて書く**（読んで確かめた、で構わない。
    **緑になっていないことを隠さない**）

20. **④は PR の state と `origin/main` の頭を毎回見る。**
    `git fetch` と `git diff` だけでは、**マージされたことに気づけない。**
    2026-08-14 に実際に起きた —— ④が 01:10 に「IPv6 の脚が開いている」と
    指摘し、**その 9 分後に社長が main へマージした。**④のレポートには
    PR 本文から引いた「マージ・本番設定変更・公開は未実施」が残っており、
    **9 分後に事実でなくなった。**
    見るのは 2 つだけ: **PR の open / merged / closed** と
    **`git fetch origin main && git log --oneline -1 origin/main`。**

    - **まとめの行には、必ず分母を書く（2026-08-17 の⑤裁定）。**
      「3 件中 3 件」「全 2 件のうち一致 1・比べられない 1」
      「4 か所のうち 4 か所を確認」。**「OK」とだけ書けるのは、
      分母と分子が一致しているときだけ。**

      **なぜ規則にしたか**: 2026-08-16〜17 の 1 日で、**同じ 1 つの形の
      間違いを 19 回書いた** —— 「push した」（見たのはローカル）／
      「原本は読めない」（試したのは取得口 1 つ）／「7.0 MB」（測ったのは
      mp4 だけ）／「変異 5 通り捕捉」（置いた書庫は 1 本）／
      「gdp の新規なし」（見たのは Issue #1 だけ）／
      「OK」（比べたのは 1 件、素材は 2 件）。**全部が「部分を測って
      全体を語る」である。**

## 環境メモ（このリポジトリで実際に踏んだものだけ書く）

  落ちる（`@eslint/eslintrc` が見つからない）。**先に `npm ci` を実行する**

  `.next/types/validator.ts(156,39): error TS2307: Cannot find module

  `.next` に残した古い生成物を `tsc --noEmit` が読むためで、
  **`npm run build` を 1 回通せば消える**（build が `.next` を作り直す）。

  変更を `git stash` して lint が通ることを確かめ、無関係だと判定した。

  > 自分の変更が壊したのかどうかを毎回 stash して確かめることになる。

  `server/api.mjs` を背景で起動したまま次の周に入ると、**古いビルドと古い
  置き場を測ることになる。**新しく起動したほうは port が埋まっていて
  黙って死ぬので、**エラーも出ない。**
