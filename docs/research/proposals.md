# 提案（役割①の出力）

毎時、役割①が書き手の体験・人が集まり残るか（集客/定着）の観点で 1 件書く。
新しいものを上に。役割②はここの最新を読んで設計する。
標準制約（決済を持たない・依存を増やさない・数字を競争にしない・
個人単位の行動計測をしない・検査/認証/上限を緩めない・第三者 JS を使わない）に
触れる提案は **要判断** と明記し、人が決めるまで役割②以降に流さない。

書式:

## <日時> <提案名>
- 状態: 未設計 / 設計済み / 実装済み / 要判断
- 何を: / なぜ: / 期待効果: / 根拠の事例: case-studies.md の番号

---

## 2026-08-14 04:10 JST **「公開する」が何をするのかを、押す前に書き手に伝える**

- 状態: **未設計**（②へ。標準制約に触れない）
- 根拠の事例: case-studies.md **48**（RFC 6721）
- **U-1 とは別の話。**U-1 は「事故で公開されるのを止める」。
  こちらは「**本人が意図して公開したとき、何が起きるかを知らせる**」

### 現物（`origin/main` `38a76eb`・`app/write/page.common.tsx:483-484`）

> 公開すると **Story 一覧** と**あなたの個人ページ**に載ります。
> 下書きはあなたにしか見えません。

**書かれているのは「2 つのページに載る」だけ。**実際に起きるのは:

| 起きること | 書かれているか | 取り消せるか |
| --- | --- | --- |
| Story 一覧に載る | **書いてある** | 取り消せる |
| 個人ページに載る | **書いてある** | 取り消せる |
| `/story/<id>/` という URL ができる | **書いていない** | URL は消える |
| **RSS で配られる**（`/api/feeds/stories.xml` と作者別フィード） | **書いていない** | **配られた先からは取り消せない**（case-studies 48） |

### 何を

**`app/write/page.common.tsx` の 483〜484 行の 2 文に、1 文足すだけ。**

```
（いま）公開すると Story 一覧 とあなたの個人ページに載ります。
       下書きはあなたにしか見えません。

（提案）公開すると Story 一覧・あなたの個人ページ・RSS に載ります。
       あとで下書きに戻せますが、RSS で受け取った人の手元からは消えません。
       下書きはあなたにしか見えません。
```

**画面の作りも、データも、URL も変えない。文言だけ。**

### なぜ（書き手の体験）

**「あとで下書きに戻せる」は本当**（`status` を `draft` に戻せば
`latestPublic()` から外れる）。**だから書き手は「戻せる」と思って押す。**
**その理解は、RSS については間違っている。**

**間違った安心を与えたまま押させるのは、この場所がやってはいけないこと。**
CreatorYard は「**作りかけを出していい場所**」を名乗っている。
**作りかけを出しやすくするために「戻せる」と思わせているなら、
戻せない部分は先に言わなければならない。**

「怖くさせる」のではありません。**RSS に載ることは価値**（読者に届く）です。
**価値と一方通行性を、同じ 1 文で伝えます。**

### なぜ（集客・定着）

- **A-8（GitHub 活動の自動記録）が入ると、公開の回数が桁で増えます。**
  1 回だけなら「まあいいか」で済むことが、**毎日になると効いてきます**
- **RSS は「押し出す」経路**なので、**購読者にとっての信用**にも関わります。
  取り消したはずのものが手元に残っている状態は、**読む側の信用も削ります**

### 期待効果

- 書き手が**知ったうえで**押せる
- **公開を減らす方向には働かない**（RSS に載る＝届く、と読めるため）

### ②へ渡すときの注意（①が確かめた範囲）

- **①は文言を確定していません。**上は例です。②が決めてください
- **`app/write/page.common.tsx` は共通ファイル**（static / server の両方）。
  **1 か所直せば両方に効く**（③が二重に直さないように）
- **RSS のパスを本文に埋め込まない。**`lib/og.ts` の `SITE_FEED` が正
- **急ぎません。**U-1 →（T-1a）→ 画像の説明 の後で構いません。
  **ただし A-8 の実装より前に入れること** —— 自動記録が入ってからでは、
  **知らないまま毎日配られた後**になります

## 2026-08-14 02:10 JST **画像の説明は「任意の空欄」ではなく「答えられる問い」で取る**

- 状態: **未設計**（②へ。標準制約に触れない）
- 根拠の事例: case-studies.md **47**
- **gdp の提案に乗る。**置き換えではなく、**1 か所だけ足す。**

### gdp が 08-14 に出した最小修正案（そのまま生きている）

> 1. 画像選択時に「画像の説明（任意）」を1欄だけ追加（短い上限を設定）
> 2. `StoryImage`／保存レコード／APIへ説明文字列を追加し、サーバーで文字数・型を検証
> 3. 説明ありは`alt`へ、説明なしは明示的に装飾扱いのままにする
> 4. 既存Storyは後方互換で説明なしとして読めるようにする
> 5. 投稿・編集・公開・API・HTML出力の回帰試験を追加

**構造としては正しい。**①はこれに反対しない。`origin/main` を読んで
**現物も確かめた**（`alt=""` が 2 か所、`StoryImage` に説明の場所が無い）。
gdp が「タイトルを自動で `alt` へ入れるだけでは画像内容の説明にならない」と
して退けたのも正しい。

### ①が足す 1 点 —— **「任意」のままだと、ほぼ全部が空欄になる**

これは書き手が不親切だからではない。**空欄のラベルが「画像の説明（任意）」だと、
書き手には「技術的な作業」に見える。**自分に読者がいる実感が無い立ち上げ期に、
**誰のためか分からない作業**を書き手はしない。**入れても使われない欄が
1 つ増えるだけ**で終わる可能性が高い。

**何を: ラベルを「説明」ではなく、答えられる問いにする。**

```
（いまの案）画像の説明（任意）        ← 何を書けばいいか分からない
（提案）  この画像で、何が見えていますか？（任意）
          例: エラーが出ている設定画面 / 影が二重に出ているところ
```

**これは gdp の 5 項目の 1 番だけを言い換えるもので、2〜5 は変えない。**

### なぜ（書き手の体験）

CreatorYard の Story に貼られる画像は、**多くが「つまずいている画面」**です
（SPEC §1 の「悩み」欄と同じ役割）。**書き手はその中身を本文で既に言葉にしている。**
だから「説明を書け」は新しい作業に見えるが、**「何が見えていますか」なら、
すでに頭の中にある言葉をそのまま置ける。**

**書き手にとっての意味も変わる。**「技術的に必要な欄」ではなく
**「読む人に伝わるように言い直す欄」**になる。この場所は
**制作の途中を人に見せる練習の場**なので、その練習の一部になる。

### なぜ（集客・定着）

- **共有したときに効く。**画像しか無い Story は、リンクを貼っても
  何の話か分からない。説明があれば**本文の要約としても効く**
- **①は「読み上げ利用者が何人いるか」を推測しない。**確かめられない
  （個人単位の計測をしないので、今後も分からない）。**分かるのは
  「いま `alt=""` と宣言している」ことだけで、それは事実と食い違っている**

### 期待効果

- 空欄率が下がる（**確かめられないので、目標値は置かない**）
- 画像しか無い Story が、共有先で意味を持つ

### ②へ渡すときの注意（①が確かめた範囲）

- **①は実装可否を判断していない。**`StoryImage` はデータモデルなので、
  **既存 Story の後方互換**（gdp の 4 番）が本体。②が範囲を決める
- **上限を必ず置く。**説明は公開 HTML の属性値に入る。**長さと文字種を
  サーバーで検査する**（`normalizeSources` と同じ形）
- **「任意」は維持する。**必須にすると画像を貼らなくなる。
  **問いを変えるだけで、強制はしない**
- **急がない。**⑤が③に渡した **IPv6**（高・時限つき）と、**PR #5 の
  nanoid**（High・CVSS 8.2）より**後**

## 2026-08-14 00:10 JST **書き手に見せていない項目を、書き手の保存操作で変えない**

- 状態: **未設計**（②へ。標準制約に触れないので流してよい）
- 根拠の事例: case-studies.md **44・45**
- きっかけ: gdp が 08-14 に見つけて直した不具合（`388afe9` / `654dd70`）。
  ①はこの直しを**追認しに来たのではなく**、同じ形が他に無いかを数えに来た。

### 数えた結果（推測なし・PR #4 head `654dd70` を読んだ）

`update()` が入れ替える項目は **9 つ** ——
`status` / `title` / `body` / `tools` / `toolTags` / `topicTags` /
`gameUrl` / `hurdle` / `sources`。うち**現状維持のガードが在るのは
`image` と `sources` の 2 つだけ**（`image` は最初から、`sources` は今回）。

**いま壊れているものは他に無い。**編集画面（`app/write/page.common.tsx`）は
読み込み時に既存値を state へ入れ（91〜95 行）、保存時に 8 項目すべてを
送り返している（176〜179 行）ので、往復して戻る。**ここは確かめた。**

**つまり「もう 1 件見つけた」ではない。危ないのは次の 1 つ。**

### 何を

`update()` の形を、**項目ごとの手当てから、既定の振る舞いへ**変える。

- **画面が送ってこなかった項目は、触らない**（＝ RFC 7396 の `undefined`）
- **消したいときは、明示的に空を送る**（＝ RFC 7396 の `null`）
- 新しい項目を足したとき、**編集フォームに欄を作らなくても消えない**のが既定

### なぜ（書き手の体験）

**書き手が最も裏切られたと感じる壊れ方は、「自分が触っていないものが、
自分の保存で消える」こと。**しかも今回は**消えたことに気づけない** ——
`sources` は編集画面に欄が無いので、書き手の目の前に「消えた」跡が残らない。
公開ページを見に行って初めて、根拠リンクが無いことに気づく。

**制作記録は「後から足していくもの」**（case-studies 2・Zenn のスクラップ）
という前提でこの場所を作っている以上、**編集して保存するのは日常操作**。
日常操作が黙って何かを削るなら、書き手は編集そのものを避けるようになる。

### なぜ（集客・定着）

社長の 08-11 の転換（A-8＝ GitHub の活動から下書きを作る）が入ると、
**`sources` のように「自動で入るが、画面に欄が無い」項目が一気に増える。**
今回の穴は**転換後に最も踏みやすい形**で、しかも**踏んだ人が気づかない**。
自動で入った内容が編集のたびに消える場所は、二度目が無い。

### 期待効果

- 新しい項目を足すときに、**フォームの欄を先に作らなくても安全**になる
- 「消える／残る」の判断が**1 か所**に集まり、④が見る場所が減る
- 規格（RFC 7396）と同じ意味論なので、**説明が要らない**

### ②へ渡すときの注意（①が確かめた範囲）

- **①はこの提案の実装可否を判断していない。**`...fields` を畳む形に触るので、
  `hurdle` / `toolTags` など**全項目の回帰試験が要る**。②が範囲を決める
- **配列を 1 件だけ消す操作は別問題。**RFC 7396 は配列を丸ごと置換と定める
  （case-studies 45）。`sources` を 1 件外す UI を作るなら設計が別に要る
- **急がない。**いま壊れているものは無い。⑤が③に渡した nginx の 2 件
  （公開した瞬間に成立する穴）より**後**でよい

## 2026-08-10 20:10 JST **RSS の URL が 3 層でずれている**（gdp の条件 3 に直接ぶつかる・実測あり）

### 提案する直し方（②が 3b の設計で決める。①は決めない）

**選べる形が 2 つある。どちらも条件 3 を満たすが、性質が違う。**

| | 案 X: 広告する URL を API の実体に合わせる | 案 Y: nginx で書き換える |
| --- | --- | --- |
| 広告する URL | `/api/feeds/stories.xml`・`/api/feeds/creators/<handle>.xml` | `/stories/feed.xml`・`/creators/<handle>/feed.xml` |

| 見た目 | 購読者に `/api/` が見える | きれい |
| **設定を忘れたときの壊れ方** | **壊れない** | **404。しかも購読者の手元に残った URL は直せない** |
| 配備の手間 | 無し | nginx 設定が本番と例で食い違うと事故 |

**①の見立て**: **案 X を推す。**理由は「壊れ方」の欄。RSS の URL は
**購読の永続契約**で、あとから直せない（この枝が `CY_SITE_ORIGIN` の既定値を

### ほかに確かめたこと

| 見たもの | 結果 |
| --- | --- |

### 提案する直し方（1 行）

```js
const collator = new Intl.Collator('ja')
const byName = (a, b) => collator.compare(a, b) || (a < b ? -1 : a > b ? 1 : 0)
```

`||` の右側は**コードポイント順**で、同じ 2 語なら必ず同じ答えを返す。
これで**入力順に依存しなくなる**。
