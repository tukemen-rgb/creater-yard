# 提案（役割①の出力）

毎時、役割①が書き手の体験・人が集まり残るか（集客/定着）の観点で 1 件書く。
新しいものを上に。役割②はここの最新を読んで設計する。
標準制約（決済を持たない・依存を増やさない・数字を競争にしない・
個人単位の行動計測をしない・検査/認証/上限を緩めない・第三者 JS を使わない）に
触れる提案は **要判断** と明記し、人が決めるまで役割②以降に流さない。

書式:

## <日時> <提案名>
- 状態: 未設計 / 設計済み / 実装済み / 要判断
- 何を: / なぜ: / 期待効果: / 根拠の事例: case-studies.md の番号

---

## 2026-08-09 09:14 JST sitemap の lastmod は Story の updatedAt から作る（ビルド時刻を使わない）
- 状態: 設計済み（designs 03:22 段階 A に反映 2026-08-09 09:20。着手は社長判断待ち）
- 何を: 公開運用設計 段階 A の sitemap.xml の項に、lastmod の作り方を
  1 行で確定させる。
  - **Story: `lastmod` は `updatedAt`**（保存済みの値）から作る
  - **タグページ・個人ページ: そのページに載る公開 Story の `updatedAt` の
    最大値**。載る Story が無いページは sitemap に出さない
  - **固定ページ（トップなど）: 内容を変えたときだけ手で更新**する日付か、
    その HTML を生成したソースの更新日。**定期ビルドで動かさない**
  - **禁止: ビルド時刻・`out/` のファイル mtime・`new Date()` を lastmod に
    使わない**。理由をコードのそばにコメントで残す
- なぜ: 焼き込みは公開ページを**毎回全部書き出す**ので、ファイルの更新時刻から
  lastmod を作ると全ページが毎回「更新された」ことになる。Google は
  lastmod を「**一貫して、検証可能な形で正確なとき**」にだけ使うと明記して
  おり（実際のページ更新と突き合わせる）、毎回全更新のサイトマップは
  その条件を外れて **lastmod ごと無視される**。sitemap を出す目的
  （新しい Story に早く気づいてもらう）が消える。
  素直に書くと踏む種類の間違いなので、実装前に設計で潰す
- 期待効果: 書き手が Story を直したときだけ「更新された」と伝わる。
  制作記録は**後から追記される**形式（つまずきが解決したら書き足す）なので、
  更新を正しく伝えられること自体が集客・定着に効く
- 付随して確定できること（設計の迷いを減らす）:
  - 送信は robots.txt の `Sitemap:` 行で足りる（設計済み・追加実装なし）
  - **sitemap の分割は作らない**。上限は 50,000 URL で、MVP の規模とは桁が違う
  - **Search Console への登録は要判断**（アカウントが要る）。取得日時と
    処理エラーが見えるので公開後の確認は楽になるが、②以降には流さない
- 根拠の事例: case-studies.md の 24
